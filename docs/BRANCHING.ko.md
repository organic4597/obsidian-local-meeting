# 브랜치와 릴리스 운영

- `main`: 배포 기준 코드와 문서. 기본 브랜치는 그대로 유지한다.
- `develop`: 다음 버전의 변경사항을 통합하고 검사하는 개발 브랜치.
- `release/0.10.0`, `release/0.11.0`과 `release/0.12.0`: 해당 버전의 검증·릴리스 준비를 별도로 이어가는 브랜치. 새 릴리스 준비 시 `release/<버전>`을 `develop`에서 분기한다.
- 기능 및 수정은 필요에 따라 `feature/<이름>` 또는 `fix/<이름>`에서 작업하고 `develop`으로 합친다. 릴리스 브랜치는 버전·문서·검증과 필요한 수정에 집중한다.
- 검증이 끝난 릴리스는 `main`에 반영하고 해당 코드 커밋에 `v<버전>` 태그를 붙인다. 릴리스 준비 중 수정은 `develop`에도 반영한다. 브랜치를 합치거나 보호 설정을 변경할 때는 실제 변경 사항을 검토한다.
- 0.1.0~0.10.0 태그와 GitHub 릴리스는 과거 커밋을 기준으로 소급 정리했다. 0.10.0은 당시 앱 클릭 재생이 미검증이어서 프리릴리스로 표시한다. 클릭 재생은 이후 0.11.0에서 확인했다. 다른 과거 0.x 개발판도 소급 생성한 프리릴리스이며 당시 검증 범위를 참조한다.
- `docs/releases/`의 각 파일을 GitHub 릴리스 본문과 동일하게 유지한다. 릴리스에는 모델 가중치·회의 녹음·개인 설정·토큰을 넣지 않는다. 과거 버전의 설치용 바이너리는 이번에 재구성하거나 첨부하지 않았다.

릴리스 파일의 본문은 변경사항이며, 실험 근거와 자세한 검증 기록은 [구현 상태](STATUS.ko.md)를 참고한다.
